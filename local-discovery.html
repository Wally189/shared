Generic method — local evidence only when authorised

Local Organisation Discovery

Before Copilot says how a particular organisation “does things”, it should identify the organisation from the user's authorised context, reconstruct the current public local governance/process baseline, and label what it still does not know. Only then should it interpret an internal tracker, procedure or inherited habit supplied through an approved workplace route.

This public page deliberately does not identify any employer or authority. If the organisation is not explicitly named by the user or clearly established from authorised workplace context in the current session, Copilot should state ORGANISATION UNKNOWN and ask.

The evidence labels

LabelMeaning
PUBLICLY VERIFIEDCurrent proposition supported by an official organisation, governance-portal or legislation source.
LOCAL-USER-SUPPLIEDInformation or document supplied through a permitted workplace route. Useful locally; not suitable for publication merely because Copilot has seen it.
LOCAL-UNVERIFIEDAcronym, habit, tracker or claim whose exact current function/authority has not yet been established.
INFERENCEA reasoned hypothesis. It must be tested before it becomes process design.

How to identify the organisation

Use only information legitimately available in the current workplace interaction: the user naming the organisation, an approved document, an organisation/tenant identity shown to Copilot, or another explicit authorised signal. State what established the identity. Do not infer the employer from this website, geography, writing style or personal assumptions.

Public local-discovery order

  1. Official governance/democracy landing page. Find the public description of meetings, decisions, forward work and transparency.
  2. Current constitution or governing documents. Record version/currentness before relying on it.
  3. Enabling instruments. Identify the legislation, orders or other instruments that establish relevant powers and structures.
  4. Current bodies. Reconstruct committees, executive/mayoral arrangements, scrutiny, audit and other governance-relevant bodies from current official records.
  5. Forward work. Inspect the forward plan or equivalent: decision type, proposed decision-maker, timing and related documents.
  6. Officer / delegated decisions. Inspect current published records and decision notices/forms where publicly available.
  7. Published assurance / accounts / frameworks. Use these to discover control structures and historical process descriptions, but label their date.
  8. National-local cross-check. Use the Governance Localiser to check that the local process fits current law and current local governing documents.

Acronyms and inherited tracker names

Never guess an acronym because it looks familiar. If current public or approved local evidence defines it, record that definition and source. If not, label it LOCAL-UNVERIFIED and ask what it means, what it tracks, who uses it and what outcome depends on it.

The local-process crosswalk

When the user supplies an approved local artefact—decision tracker, spreadsheet, SOP, intranet instruction, mailbox workflow—build this table before proposing replacement:

Questions Copilot must ask about a local tracker

  • What does the name/acronym mean here?
  • What is the tracker for: pipeline, clearance, publication, decision record, action follow-up, or several things?
  • Which fields are required by law/local governance/process, and which exist because “we've always had that column”?
  • Who creates a row, who updates it, who relies on it and who closes it?
  • What event starts the process? What event proves completion?
  • Where is the canonical record once complete?
  • What is copied manually into/from committee software, email, Word forms or another spreadsheet?
  • What colours/free-text codes have hidden meaning?
  • Are there linked workbooks, queries, formulas or downstream reports?
  • What fails if the tracker is unavailable?
  • What current local instruction authorises or describes the workflow?

Then find the least disruptive option

OPTION A — REPAIR
Keep the current tracker; remove defects, standardise fields, document ownership.

OPTION B — CONSOLIDATE
Keep familiar tools but remove duplicate trackers or manual re-entry.

OPTION C — STRUCTURE
Move shared finite state into an appropriate List/library/workflow while preserving familiar views.

OPTION D — INTEGRATE / AUTOMATE
Only after the process is stable: use supported queries, connectors, rules or controlled automation to reduce deterministic re-keying.

The test is not “is the replacement newer?” It is “does this remove real duplication/risk while preserving authority, history and usability?”

People: gentle without games

Do not label a colleague insecure, technophobic or obstructive. Record observable barriers: uncertainty, skill/confidence, workload, process knowledge, stated objection, dependency or loss of a familiar control. A sceptical experienced colleague can be an excellent tester of edge cases.

The adoption sequence is: show the existing problem → preserve the useful control → prototype beside it → let the user break it → prove the outcome → write the plain-English SOP → retire the duplicate only when safe.

Local Discovery prompt

GOAL: Build the current public local Democratic Services/process baseline for my organisation and [topic] before advising me.
IDENTITY: Establish the organisation only from what I name or authorised workplace context visible in this session. If it is not reliable, state ORGANISATION UNKNOWN and ask.
SOURCES: Current official organisation website/governance portal, current constitution or governing documents, enabling instruments, bodies, meetings, forward plan or equivalent, officer/delegated decisions, published decision records, legislation and current official guidance.
CLASSIFY: PUBLICLY VERIFIED / LOCAL-USER-SUPPLIED / LOCAL-UNVERIFIED / INFERENCE.
DO NOT: infer internal acronyms, publish internal material, or assume an old public document describes the current internal process.
THEN: compare the public baseline with the local tracker/process I describe or am permitted to attach.
OUTPUT:
1. Organisation identity and evidence for it
2. Public source map
3. Formal body/decision/process map
4. What is genuinely known about the local artefact
5. Unknowns/questions
6. Duplication and hidden controls
7. No more than 3 improvement options
8. One reversible next step
9. Plain-English SOP for the step
10. Progress Block for OneNote
STOP after the one next step unless I ask for the full roadmap.
